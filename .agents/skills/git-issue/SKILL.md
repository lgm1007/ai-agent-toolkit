# Git 이슈 생성

사용자가 설명한 내용을 요구사항 중심의 GitHub 이슈로 정리해 생성한다.
본문 조합, 검증, 생성은 반드시 `scripts/create-issue.sh`로 수행해서, 누가 실행하더라도 같은 구조의 이슈를 얻도록 한다.
이슈를 생성하려면 GitHub CLI(`gh`)가 설치되어 있고 인증되어 있어야 한다.

## 이슈 작성 규칙

### 제목

- 형식은 `<type>: <제목>`이다. (`feat: 카카오 소셜 로그인 기능 구현`)
- type은 커밋 메시지 규칙과 같은 6개 중 하나를 소문자로 쓰고, 콜론 뒤에 공백 한 칸을 둔다.
  - feat: 새 기능 추가
  - fix: 버그 수정
  - refactor: 리팩토링 및 코드 정리
  - chore: 환경 설정/빌드 작업
  - docs: 문서 및 주석 작성
  - test: 테스트 코드
- 제목은 해결할 작업을 한 줄로 요약하고, 끝에 마침표를 찍지 않는다.
- 제목 줄은 `type: `을 포함해 72자 이내로 작성한다.
- 한국어 제목은 "로그인 기능 추가"처럼 명사형으로 끝낸다.

### 본문 구조

스크립트가 아래 순서로 본문을 조합한다. 내용이 없는 선택 섹션은 출력하지 않는다.

| 섹션 | 필수 여부 | 작성 내용 |
|---|---|---|
| 개요 | 필수 | 작업의 배경과 목적을 2~3문장으로 작성 |
| 재현 방법 | fix만 선택 | 문제를 재현하는 순서 |
| 기대 동작 | fix만 선택 | 원래 기대한 동작 |
| 실제 동작 | fix만 선택 | 실제로 발생한 동작과 오류 메시지 |
| 요구사항 | 필수 | 구현하거나 수정해야 할 항목 (체크리스트) |
| 완료 조건 | 필수 | 작업 완료 여부를 판단할 검증 기준 (체크리스트) |
| 참고 사항 | 선택 | 관련 이슈, 문서 링크, 제약 사항, 확인이 필요한 사항 |

### 요구사항과 완료 조건 작성 기준

- 요구사항 한 항목에는 요구사항 하나만 쓴다.
- 구현 방법보다 달성해야 할 결과를 쓴다. 사용자가 구현 방법을 지정한 경우에만 방법을 쓴다.
- 완료 조건은 확인할 수 있는 형태로 쓴다. ("로그인이 잘 된다" ✗ → "카카오 계정으로 로그인하면 JWT가 발급된다" ✓)
- 사용자가 말하지 않은 요구사항을 추측해서 추가하지 않는다. 필요해 보이는 항목은 참고 사항에 "확인 필요"로 적는다.
- 버그 이슈에서 사용자가 재현 방법, 기대 동작, 실제 동작을 알려 주지 않았다면 해당 섹션을 임의로 채우지 않는다.

### 이슈 분리 기준

- 서로 독립적으로 완료할 수 있는 작업이 섞여 있으면 이슈를 나눌지 사용자에게 제안한다.
- 이슈 하나는 브랜치 하나와 PR 하나로 끝낼 수 있는 크기로 작성한다.

### 작성 예시

사용자 입력: "카카오 로그인 붙여야 해. 기존 회원이면 계정 연결하고, 신규면 가입시켜야 하고. 토큰은 기존 JWT 방식 그대로."

```markdown
feat: 카카오 소셜 로그인 기능 추가

## 개요
카카오 계정으로 로그인할 수 있도록 소셜 로그인 기능을 추가한다.
기존 회원과 신규 사용자 모두 카카오 계정으로 서비스를 이용할 수 있게 하는 것이 목적이다.

## 요구사항
- [ ] 카카오 OAuth 인증으로 로그인할 수 있다
- [ ] 기존 회원이면 카카오 계정을 기존 계정에 연결한다
- [ ] 가입 이력이 없으면 신규 회원으로 가입시킨다
- [ ] 로그인에 성공하면 기존 JWT 방식으로 토큰을 발급한다

## 완료 조건
- [ ] 기존 회원이 카카오 계정으로 로그인하면 기존 계정으로 로그인된다
- [ ] 신규 사용자가 카카오 계정으로 로그인하면 회원이 생성되고 JWT가 발급된다

## 참고 사항
- 기존 회원을 판별하는 기준(예: 이메일 일치 여부) 확인 필요
```

## 실행 절차

1. 사용자 입력에서 목적, 요구사항, 완료 조건, 버그 정보, 참고 사항을 추출한다.
2. 작업의 목적(무엇을 왜 하는지)을 알 수 없으면 이슈를 만들기 전에 사용자에게 질문한다.
3. type을 결정하고 제목을 작성한다.
4. `--dry-run`으로 실행하고, 출력된 제목, 라벨, 본문을 사용자에게 보여 주며 생성 승인을 받는다.
5. 승인을 받으면 같은 인자에서 `--dry-run`만 빼고 실행한다.
6. 종료 코드가 0이 아니면 아래의 "종료 코드별 대응" 표에 따라 처리한다.
7. 이슈 번호와 URL을 사용자에게 보고한다. 이어서 브랜치를 만들 때는 git-branch 스킬에 `--issue <번호>`를 전달한다.

이슈 생성은 저장소에 접근할 수 있는 모든 사람에게 공개되는 작업이므로 사용자 승인 없이 실행하지 않는다. 사용자가 확인 없이 바로 생성하라고 명시한 경우에만 4번을 생략한다.
`gh issue create`를 직접 실행해서 이슈를 만들지 않는다. 스크립트가 실패하면 우회하지 말고, 원인을 해결하거나 사용자에게 보고한다.

## 스크립트 사용법

스크립트는 이 SKILL.md가 있는 디렉터리를 기준으로 `scripts/create-issue.sh`에 있다. Claude Code에서는 `<스킬 디렉터리>` 자리에 `${CLAUDE_SKILL_DIR}`를 사용한다.
대상 저장소 안에서 실행하거나, `--repo`로 저장소를 지정한다.

```bash
bash <스킬 디렉터리>/scripts/create-issue.sh <type> "<제목>" --summary "<개요>" \
  --requirement "<요구사항>" --criteria "<완료 조건>" [옵션]

# 예시
bash <스킬 디렉터리>/scripts/create-issue.sh fix "배송 중인 주문 취소 시 500 에러 발생 문제 수정" \
  --summary "배송이 시작된 주문을 취소하면 서버에서 500 에러가 발생한다." \
  --step "배송 중 상태인 주문의 상세 화면으로 이동" \
  --step "주문 취소 버튼 클릭" \
  --expected "취소할 수 없다는 안내 메시지가 표시된다" \
  --actual "500 Internal Server Error 응답이 반환된다" \
  --requirement "배송 중인 주문의 취소 요청을 거절한다" \
  --criteria "배송 중인 주문을 취소하면 400 응답과 안내 메시지를 반환한다" \
  --dry-run
```

| 옵션 | 설명 |
|---|---|
| `--summary <내용>` | 개요 섹션의 내용이다. 필수 옵션이다. |
| `--requirement <내용>` | 요구사항 한 항목을 추가한다. 1개 이상 필수이며 여러 번 지정할 수 있다. |
| `--criteria <내용>` | 완료 조건 한 항목을 추가한다. 1개 이상 필수이며 여러 번 지정할 수 있다. |
| `--step <내용>` | 재현 방법 한 단계를 추가한다. fix 전용이며 여러 번 지정할 수 있다. |
| `--expected <내용>` | 기대 동작을 지정한다. fix 전용이다. |
| `--actual <내용>` | 실제 동작을 지정한다. fix 전용이다. |
| `--note <내용>` | 참고 사항 한 항목을 추가한다. 여러 번 지정할 수 있다. |
| `--label <이름>` | 라벨을 추가한다. 여러 번 지정할 수 있으며, 저장소에 없는 라벨은 오류로 처리한다. |
| `--assignee <사용자>` | 담당자를 지정한다. `@me`를 사용할 수 있고, 여러 번 지정할 수 있다. |
| `--milestone <이름>` | 마일스톤을 지정한다. |
| `--repo <owner/repo>` | 대상 저장소를 지정한다. 생략하면 현재 디렉터리의 저장소를 사용한다. |
| `--allow-duplicate` | 같은 제목의 열린 이슈가 있어도 생성한다. 사용자 승인이 필요하다. |
| `--dry-run` | 검증과 본문 미리보기만 수행하고 이슈를 생성하지 않는다. |

- type에 맞는 라벨이 저장소에 있으면 자동으로 추가한다. type과 같은 이름의 라벨(`feat` 등)을 먼저 찾고, 없으면 GitHub 기본 라벨(feat → `enhancement`, fix → `bug`, docs → `documentation`)을 사용한다.
- 저장소에 없는 라벨을 새로 만들지 않는다. 라벨 생성이 필요하면 사용자에게 요청한다.

실행 결과는 표준 출력에 `key=value` 형식으로 출력되고, 진행 로그, 경고, 본문 미리보기는 표준 에러에 출력된다.

```
RESULT=created
NUMBER=128
URL=https://github.com/owner/repo/issues/128
REPO=owner/repo
TYPE=feat
TITLE=feat: 카카오 소셜 로그인 기능 추가
LABELS=enhancement
```

- `RESULT`: 이슈를 생성했으면 `created`, `--dry-run`으로 실행했으면 `dry-run`
- `NUMBER`, `URL`: 생성한 이슈의 번호와 주소 (`--dry-run`이면 빈 값)
- `LABELS`: 이슈에 붙인 라벨 목록 (쉼표로 구분)

## 종료 코드별 대응

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 성공 | `--dry-run`이면 미리보기를 보여 주고 승인을 받는다. 생성했으면 번호와 URL을 보고한다. |
| 1 | gh 명령 실패 | 오류 메시지를 사용자에게 보고한다. |
| 2 | 인자 오류 | 메시지에 맞게 type, 제목, 섹션 내용을 고쳐 다시 실행한다. |
| 3 | 제목 줄 72자 초과 | 제목을 줄이고, 자세한 내용은 개요로 옮겨 다시 실행한다. |
| 4 | gh 미설치 또는 미인증 | 사용자에게 `gh` 설치나 `gh auth login` 실행을 요청한다. 인증 명령을 대신 실행하지 않는다. |
| 5 | 저장소에 없는 라벨 | 사용할 수 있는 라벨 목록을 보여 주고, 어떤 라벨을 쓸지 사용자에게 확인한다. |
| 6 | 같은 제목의 열린 이슈 존재 | 기존 이슈 URL을 보여 주고, 기존 이슈를 사용할지 새로 만들지 사용자에게 확인한다. |
| 7 | 대상 저장소 확인 실패 | GitHub 원격 저장소가 연결되어 있는지 확인하고, 필요하면 `--repo`로 저장소를 지정한다. |

## 주의 사항

- 비밀번호, API 키, 토큰, 개인정보, 내부 서버 주소를 이슈에 적지 않는다. 로그를 첨부할 때는 민감한 값을 가린다.
- 공개 저장소라는 경고가 나오면, 이슈 내용이 외부에 공개된다는 사실을 사용자에게 알린다.
- 이슈를 닫거나 수정하거나 삭제하는 작업은 이 스킬 범위에 포함되지 않는다.
