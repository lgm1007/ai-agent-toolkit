# 산출물 리뷰

설계 문서와 코드 변경 사항을 같은 기준으로 리뷰하고, 결과를 리뷰 보고서로 남긴다.
리뷰 근거 수집은 `scripts/review-context.sh`, 보고서 생성은 `scripts/create-report.sh`, 보고서 검증은 `scripts/check-report.sh`로 수행해서, 누가 리뷰하더라도 같은 절차와 형식으로 결과가 남도록 한다.

## 리뷰 대상

| 대상 유형 | 입력 | 리뷰 범위 |
|---|---|---|
| 설계 문서 (`doc`) | 설계 문서 경로 | docs-create 스킬로 작성한 구현 설계 문서 |
| 코드 변경 (`code`) | 현재 작업 브랜치, 기준 브랜치(선택), 설계 문서 경로(선택) | 기준 브랜치와 갈라진 지점부터 현재 작업 트리까지의 모든 변경 |

- 리뷰 대상이 명확하지 않으면 사용자에게 확인한다.
- 코드 변경 리뷰에는 커밋한 변경뿐 아니라 커밋하지 않은 변경과 새로 추가한 파일도 포함한다.
- 기준 브랜치를 지정하지 않으면 develop, dev, development 중 존재하는 브랜치를 사용한다.
- 설계 문서를 지정하지 않아도, 브랜치 이름의 이슈 번호와 관련 이슈가 같은 설계 문서가 하나 있으면 함께 리뷰한다.

## 리뷰 원칙

1. 리뷰 중에는 산출물을 수정하지 않는다. 수정은 리뷰가 끝난 뒤 사용자가 요청한 경우에만 한다.
2. 모든 지적 사항에는 근거 위치(파일과 줄 번호, 또는 문서의 섹션)를 적는다.
3. 추측으로 지적하지 않는다. 관련 코드와 문서를 직접 읽고 확인한 문제만 지적하고, 확인할 수 없는 내용은 5. 확인 필요 사항에 적는다.
4. 자동 검사 결과는 지적 후보다. 실제 문제인지 확인한 뒤에 지적 사항으로 올린다.
5. 문제를 지적할 때는 구체적인 수정 제안을 함께 적는다.
6. 프로젝트의 기존 규칙과 코드 스타일을 기준으로 판단하고, 개인 취향에 가까운 의견은 낮음으로 분류한다.
7. 같은 종류의 사소한 문제가 여러 곳에 있으면 지적 사항 하나로 묶고 위치를 나열한다.

## 리뷰 관점

### 설계 문서

| 관점 | 확인 내용 |
|---|---|
| 요구사항 | 요구사항이 명확하고 검증할 수 있는지, 포함하는 범위와 포함하지 않는 범위가 분명한지 |
| 추적성 | 모든 요구사항 ID가 4.1 작업 목록과 5. 테스트 계획에 반영되었는지 |
| 설계 타당성 | 기존 코드 구조와 맞는지, 더 단순한 대안은 없는지, 설계 결정에 이유가 있는지 |
| 명세 완전성 | 데이터 모델, API, 예외 처리가 바로 구현할 수 있을 만큼 구체적인지 |
| 비기능 요구사항 | 보안, 성능, 호환성, 운영(로그, 모니터링) 고려가 빠지지 않았는지 |
| 위험과 미결정 사항 | 위험 요소마다 대응 방법이 있는지, 구현 전에 정해야 할 미결정 사항이 남아 있지 않은지 |

### 코드 변경

| 관점 | 확인 내용 |
|---|---|
| 요구사항 반영 | 설계 문서의 요구사항과 설계대로 구현했는지, 범위를 벗어난 변경은 없는지 |
| 정확성 | 로직 오류, 경계 조건, null 처리, 예외 처리, 동시성 문제가 없는지 |
| 테스트 | 변경한 동작을 검증하는 테스트가 있는지, 테스트가 의미 있는 값을 검증하는지 |
| 보안 | 입력 검증, 인증과 인가, 민감 정보 노출 문제가 없는지 |
| 성능 | 반복 조회(N+1), 불필요한 반복 처리, 과도한 메모리 사용이 없는지 |
| 유지보수성 | 중복 코드, 이름, 구조가 기존 코드 규칙과 일관적인지 |
| 호환성 | API, DB 스키마, 설정 변경이 기존 사용자나 다른 모듈에 영향을 주지 않는지 |
| 빌드 | 빌드와 테스트가 통과하는지 |

## 심각도와 결론 기준

| 심각도 | 기준 |
|---|---|
| 높음 | 버그, 보안 취약점, 데이터 손실 가능성, 요구사항 미반영, 빌드나 테스트 실패처럼 반드시 고쳐야 하는 문제 |
| 중간 | 테스트 누락, 예외 처리 부족, 설계와의 불일치, 유지보수를 크게 어렵게 만드는 구조처럼 merge 전에 고치는 것이 좋은 문제 |
| 낮음 | 이름, 가독성, 사소한 개선처럼 선택적으로 반영해도 되는 의견 |

| 결론 | 기준 |
|---|---|
| 승인 | 높음과 중간 지적 사항이 없다. |
| 조건부 승인 | 높음 지적 사항은 없고, 중간 지적 사항을 고치는 조건으로 승인한다. |
| 수정 필요 | 높음 지적 사항이 하나 이상 있다. |

`check-report.sh`는 높음 지적 사항이 있는데 결론이 수정 필요가 아니거나, 중간 이상의 지적 사항이 있는데 결론이 승인이면 규칙 위반으로 판단한다.

## 리뷰 보고서

- 보고서는 프로젝트 루트의 `docs/<YYMMDD>/<영문 대상명>-<doc|code>-review.md`에 작성한다. `<YYMMDD>`는 리뷰한 날짜다.
- 같은 대상을 같은 날 다시 리뷰하면 `-review-2.md`처럼 차수가 붙은 새 보고서를 만든다. 기존 보고서는 수정하지 않는다.
- 영문 대상명은 설계 문서의 파일 이름(확장자 제외)을 사용한다. 연결된 설계 문서가 없는 코드 리뷰는 브랜치 이름에서 prefix를 뺀 작업명(`feat/128-add-login` → `128-add-login`)을 사용한다.
- 보고서는 `templates/review-report.md` 템플릿으로 만들며, 목차는 다음과 같다.

| 섹션 | 작성 내용 |
|---|---|
| 메타데이터 표 | 리뷰 대상, 대상 유형, 리뷰 일자, 리뷰어, 리뷰 차수, 결론 |
| 1. 리뷰 요약 | 리뷰 결과 요약과 결론의 근거 |
| 2. 자동 검사 결과 | `review-context.sh`의 검사 결과 |
| 3. 지적 사항 | `\| 번호 \| 심각도 \| 위치 \| 내용 \| 제안 \|` 형식의 표 (없으면 "없음") |
| 4. 요구사항 반영 확인 | 요구사항 ID별 반영 여부(반영, 일부 반영, 미반영)와 근거 위치 |
| 5. 확인 필요 사항 | 작성자나 사용자에게 확인해야 하는 내용 |
| 6. 좋은 점 | 유지하면 좋을 설계나 구현 |

- 메타데이터의 결론은 처음에 "검토 중"으로 만들어지며, 작성을 마칠 때 승인, 조건부 승인, 수정 필요 중 하나로 바꾼다.
- 템플릿의 안내 주석(`<!-- deliverable-review: ... -->`)은 해당 섹션을 작성하면서 삭제한다.
- 자동 검사에서 민감 정보가 발견되어도 보고서에는 실제 값을 옮겨 적지 않고 위치만 적는다.

## 실행 절차

1. 리뷰 대상 유형(설계 문서 또는 코드 변경)과 대상을 확인한다.
2. 리뷰할 Git 저장소 안에서 `review-context.sh`를 실행해 리뷰 근거를 수집한다.
3. 리뷰 대상을 모두 읽는다.
   - 설계 문서 리뷰: 문서 전체와 문서가 언급한 기존 코드
   - 코드 리뷰: `DIFF_PATH`의 변경 내용, 변경한 파일의 주변 코드, 연결된 설계 문서
4. 코드 리뷰라면 빌드와 테스트 결과를 확인한다. 이번 변경에 대한 빌드 결과가 없으면 develop-by-docs 스킬의 `build.sh`나 프로젝트의 빌드 명령으로 실행한다.
5. 리뷰 관점별로 확인하고, 자동 검사 결과를 검증해서 지적 사항을 정리한다.
6. `create-report.sh`로 보고서를 만들고, 섹션별로 작성한 뒤 `check-report.sh`로 검증한다. 문제가 있으면 고친 뒤 다시 검증한다.
7. 결론, 높음과 중간 지적 사항 요약, 확인 필요 사항, 보고서 경로를 사용자에게 보고한다.

- 리뷰 결과에 따른 수정과 보고서 커밋은 사용자가 요청한 경우에만 수행한다. 보고서를 커밋할 때는 git-commit 스킬을 사용한다. (예: `docs: 카카오 소셜 로그인 코드 리뷰 보고서 작성`)

## 스크립트 사용법

스크립트는 이 SKILL.md가 있는 디렉터리를 기준으로 `scripts/`에 있다. Claude Code에서는 `<스킬 디렉터리>` 자리에 `${CLAUDE_SKILL_DIR}`를 사용한다.
설계 문서 리뷰는 docs-create 스킬의 `scripts/check-doc.sh`로 문서 구조를 검사하므로, docs-create 스킬이 같은 skills 디렉터리에 있어야 한다.

### review-context.sh

```bash
bash <스킬 디렉터리>/scripts/review-context.sh doc <설계 문서 경로>
bash <스킬 디렉터리>/scripts/review-context.sh code [옵션]

# 예시
bash <스킬 디렉터리>/scripts/review-context.sh doc docs/260915/kakao-social-login.md
bash <스킬 디렉터리>/scripts/review-context.sh code --base develop
```

| 옵션 (`code` 전용) | 설명 |
|---|---|
| `--base <브랜치>` | 기준 브랜치를 지정한다. 생략하면 develop, dev, development 중 존재하는 브랜치를 사용한다. |
| `--doc <설계 문서 경로>` | 함께 리뷰할 설계 문서를 지정한다. 생략하면 브랜치의 이슈 번호로 찾는다. |
| `--remote <이름>` | 원격 저장소 이름을 지정한다. (기본값: `origin`) |
| `--no-fetch` | 원격 저장소에 접속하지 않고 마지막으로 fetch한 기준 브랜치를 사용한다. |

자동 검사 항목은 다음과 같다. 검사 결과는 `FINDINGS_PATH` 파일에 `심각도 후보|종류|위치|내용` 형식으로 저장하고, 표준 에러에도 출력한다.

| 대상 | 검사 | 심각도 후보 |
|---|---|---|
| 설계 문서 | docs-create 문서 규칙 위반 | 중간 |
| 설계 문서 | 4.1 작업 목록이나 5. 테스트 계획에 없는 요구사항 ID | 중간 |
| 코드 변경 | 추가한 줄의 merge 충돌 표시 | 높음 |
| 코드 변경 | 추가한 줄의 비밀번호, API 키, 토큰으로 의심되는 값 (값은 기록하지 않음) | 높음 |
| 코드 변경 | 민감한 파일로 의심되는 파일 (`.env`, `*.pem`, `*.key` 등) | 높음 |
| 코드 변경 | 소스 파일은 바뀌었는데 테스트 파일 변경이 없음 | 중간 |
| 코드 변경 | 추가한 줄의 디버그 출력 (`console.log`, `System.out.print` 등) | 낮음 |
| 코드 변경 | 추가한 줄의 TODO, FIXME | 낮음 |
| 코드 변경 | 줄 끝 공백 같은 공백 오류 (`git diff --check`) | 낮음 |

```
RESULT=collected
TARGET_TYPE=code
BRANCH=feat/128-add-kakao-social-login
BASE=origin/develop
MERGE_BASE=3f2a9c1
COMMITS=3
CHANGED_FILES=12
UNCOMMITTED_FILES=2
ADDED_LINES=340
DELETED_LINES=25
TEST_FILES_CHANGED=3
DOC_PATH=/path/to/project/docs/260915/kakao-social-login.md
REQUIREMENTS=5
AUTO_FINDINGS=4
DIFF_PATH=/tmp/deliverable-review.a1B2c3/changes.diff
FINDINGS_PATH=/tmp/deliverable-review.a1B2c3/findings.txt
```

- `doc` 대상은 `TARGET_TYPE`, `DOC_PATH`, `DOC_CHECK`(valid, invalid), `DOC_ISSUES`, `DOC_STATUS`, `REQUIREMENTS`, `UNTRACED_TASKS`, `UNTRACED_TESTS`, `UNRESOLVED`, `AUTO_FINDINGS`, `FINDINGS_PATH`를 출력한다.
- `UNTRACED_TASKS`, `UNTRACED_TESTS`: 4.1 작업 목록, 5. 테스트 계획에서 참조하지 않은 요구사항 ID 목록 (쉼표로 구분)

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 수집 완료 | 결과와 자동 검사 항목을 바탕으로 리뷰한다. |
| 1 | 저장소 상태 오류 또는 필요한 스크립트 없음 | 오류 메시지를 보고한다. |
| 2 | 인자 오류 | 대상 유형과 옵션을 확인해 다시 실행한다. |
| 3 | 리뷰 대상 없음 | 설계 문서 경로를 확인하거나, 기준 브랜치와 비교해 변경 사항이 없다는 사실을 사용자에게 알린다. |
| 4 | 기준 브랜치를 찾을 수 없거나 후보가 여러 개 | 사용자에게 기준 브랜치를 확인하고 `--base`로 지정한다. |
| 5 | 원격 저장소 조회 또는 fetch 실패 | 네트워크와 인증 상태를 보고한다. 사용자가 동의하면 `--no-fetch`로 다시 실행한다. |

### create-report.sh

```bash
bash <스킬 디렉터리>/scripts/create-report.sh <doc|code> <영문 대상명> --title "<리뷰 대상 제목>" --target "<리뷰 대상>" [옵션]

# 예시
bash <스킬 디렉터리>/scripts/create-report.sh code kakao-social-login \
  --title "카카오 소셜 로그인 구현" \
  --target "feat/128-add-kakao-social-login (기준: origin/develop)"
```

| 옵션 | 설명 |
|---|---|
| `--title <제목>` | 리뷰 대상 제목을 지정한다. 보고서 제목은 `<제목> 리뷰`가 된다. 필수 옵션이다. |
| `--target <리뷰 대상>` | 메타데이터 표의 리뷰 대상에 적을 문서 경로나 브랜치를 지정한다. 필수 옵션이다. |
| `--author <이름>` | 리뷰어를 지정한다. 생략하면 Git 설정의 `user.name`을 사용한다. |
| `--root <디렉터리>` | 프로젝트 루트를 지정한다. 생략하면 Git 저장소의 최상위 디렉터리를 사용한다. |
| `--dry-run` | 보고서 경로만 확인하고 파일은 만들지 않는다. |

```
RESULT=created
REPORT_PATH=/path/to/project/docs/260915/kakao-social-login-code-review.md
REPORT_RELATIVE_PATH=docs/260915/kakao-social-login-code-review.md
REPORT_DATE=260915
REVIEW_ROUND=1
```

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 성공 | `REPORT_PATH`의 보고서를 작성한다. |
| 1 | 환경 오류 (템플릿 없음, 파일 생성 실패 등) | 오류 메시지를 보고한다. |
| 2 | 인자 오류 | 대상 유형, 영문 대상명, 제목, 리뷰 대상을 확인해 다시 실행한다. |
| 3 | 영문 대상명 50자 초과 | 핵심 키워드만 남겨 다시 실행한다. |

### check-report.sh

```bash
bash <스킬 디렉터리>/scripts/check-report.sh <리뷰 보고서 경로>
```

다음 항목을 검사한다.

- 보고서 경로가 `docs/<YYMMDD>/<영문 대상명>-<doc|code>-review(-<차수>).md` 규칙에 맞는지
- 보고서 제목(`#`)이 한 개인지, 템플릿의 필수 섹션이 순서대로 있고 내용이 작성되었는지
- 안내 주석이나 채우지 않은 템플릿 항목(`{{...}}`)이 남아 있지 않은지
- 리뷰 일자가 날짜 디렉터리와 같은지, 대상 유형이 파일 이름과 맞는지
- 결론이 승인, 조건부 승인, 수정 필요 중 하나인지
- 지적 사항이 표 또는 "없음"으로 작성되었는지, 심각도가 높음, 중간, 낮음 중 하나인지
- 지적 사항의 심각도와 결론이 결론 기준에 맞는지

```
RESULT=valid
REPORT_PATH=/path/to/project/docs/260915/kakao-social-login-code-review.md
VERDICT=조건부 승인
HIGH=0
MEDIUM=2
LOW=3
ISSUES=0
```

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 규칙에 맞는 보고서 | 결과를 사용자에게 보고한다. |
| 1 | 보고서 파일이나 템플릿을 찾을 수 없음 | 경로를 확인하고 다시 실행한다. |
| 2 | 인자 오류 | 보고서 경로를 하나만 전달해 다시 실행한다. |
| 3 | 보고서 규칙 위반 | 표준 에러에 출력된 문제를 모두 고친 뒤 다시 검증한다. |

## 주의 사항

- 리뷰 대상 산출물과 기존 리뷰 보고서를 수정하거나 덮어쓰지 않는다.
- 민감 정보로 의심되는 값은 보고서, 대화, 커밋 메시지 어디에도 옮겨 적지 않는다.
- 리뷰를 위해 빌드나 테스트를 실행할 때 DB 마이그레이션처럼 외부에 영향을 주는 작업이 포함되어 있으면 사용자에게 먼저 확인한다.
