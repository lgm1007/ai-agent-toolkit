# Git 커밋 생성

변경 사항을 분석해 규칙에 맞는 커밋 메시지를 작성하고 커밋한다.
메시지 조합, 검증, 커밋은 반드시 `scripts/commit.sh`로 수행해서, 누가 실행하더라도 같은 형식의 커밋을 얻도록 한다.

## 커밋 메시지 규칙

- feat: 새 기능 추가
- fix: 버그 수정
- refactor: 리팩토링 및 코드 정리
- chore: 환경 설정/빌드 작업
- docs: 문서 및 주석 작성
- test: 테스트 코드

### 메시지 형식

```
<type>: <제목>

<본문 (선택)>

Refs: #<이슈 번호> (선택)
```

- type은 위 6개 중 하나를 소문자로 쓰고, 콜론 뒤에 공백 한 칸을 둔다. scope(`feat(auth):`)는 사용하지 않는다.
- 제목은 무엇을 변경했는지 한 줄로 요약하고, 끝에 마침표를 찍지 않는다.
- 제목 줄은 type을 포함해 72자 이내로 작성한다.
- 제목은 저장소의 최근 커밋 메시지와 같은 언어로 작성한다. 참고할 커밋 이력이 없으면 한국어로 작성한다.
- 한국어 제목은 "로그인 기능 추가"처럼 명사형으로 끝내고, "~한다", "~했습니다" 같은 서술형은 쓰지 않는다.
- 본문은 제목만으로 변경 이유나 영향을 알기 어려울 때 작성한다. 무엇을 왜 바꿨는지 쓰고, 여러 항목은 `- `로 시작하는 목록으로 쓴다.
- 브랜치명에 이슈 번호가 있으면(`feat/128-add-...`) 스크립트가 `Refs: #128` 푸터를 자동으로 붙인다.

### type 판단 기준

- type은 브랜치 prefix가 아니라 해당 커밋의 변경 내용으로 결정한다. `feat/` 브랜치에서도 테스트 코드만 추가한 커밋은 `test:`로 작성한다.
- 한 커밋에는 한 가지 목적의 변경만 담는다. 기능 추가와 무관한 리팩토링이 섞여 있으면 파일을 나눠 스테이징하고 커밋도 나눈다.
- 아래 기준으로도 판단하기 어려우면 후보 type과 판단 근거를 제시하고 사용자에게 확인한다.

| 변경 내용 | type |
|---|---|
| 새 API, 화면, 기능 추가 (함께 작성한 테스트 포함) | `feat` |
| 잘못된 동작, 예외, 오류 수정 | `fix` |
| 동작 변경 없는 구조 개선, 이름 변경, 코드 포맷 정리 | `refactor` |
| 의존성, 빌드 스크립트, CI/CD, 환경 설정 파일 변경 | `chore` |
| README, 문서, 코드 주석만 변경 | `docs` |
| 테스트 코드만 추가하거나 수정 | `test` |

### 작성 예시

| 변경 내용 | 제목 줄 |
|---|---|
| 카카오 소셜 로그인 API 추가 | `feat: 카카오 소셜 로그인 API 추가` |
| 주문 취소 시 발생하는 NullPointerException 수정 | `fix: 주문 취소 시 NullPointerException 발생 문제 수정` |
| 결제 검증 로직을 별도 클래스로 분리 | `refactor: 결제 검증 로직을 PaymentValidator로 분리` |
| Spring Boot 3.3 버전 업그레이드 | `chore: Spring Boot 3.3 버전 업그레이드` |
| README 설치 방법 보완 | `docs: README 설치 방법 보완` |
| 회원 서비스 단위 테스트 추가 | `test: 회원 서비스 단위 테스트 추가` |

## 실행 절차

1. `git status`와 `git diff`로 변경 사항을 확인한다.
2. 커밋할 파일만 `git add <파일 경로>`로 지정해 스테이징한다. `git add -A`, `git add .`, `git commit -a`는 사용하지 않는다.
3. `git diff --cached`로 스테이징한 내용을 확인하고 type과 제목을 결정한다.
4. 스크립트를 실행한다.
5. 종료 코드가 0이 아니면 아래의 "종료 코드별 대응" 표에 따라 처리한다.
6. 커밋 해시와 제목 줄을 표준 에러로 출력된 경고와 함께 사용자에게 보고한다.

`git commit`을 직접 실행해서 커밋하지 않는다. 스크립트가 실패하면 우회하지 말고, 원인을 해결하거나 사용자에게 보고한다.
사용자가 커밋 메시지를 먼저 확인하길 원하면 `--dry-run`으로 메시지를 미리 보여 준다.

## 스크립트 사용법

스크립트는 이 SKILL.md가 있는 디렉터리를 기준으로 `scripts/commit.sh`에 있다. Claude Code에서는 `<스킬 디렉터리>` 자리에 `${CLAUDE_SKILL_DIR}`를 사용한다.

```bash
bash <스킬 디렉터리>/scripts/commit.sh <type> "<제목>" [옵션]

# 예시
bash <스킬 디렉터리>/scripts/commit.sh feat "카카오 소셜 로그인 API 추가"
bash <스킬 디렉터리>/scripts/commit.sh fix "주문 취소 시 NullPointerException 발생 문제 수정" \
  --body "- 취소할 주문이 없으면 예외 대신 404 응답을 반환" \
  --body "- 주문 상태 검증을 취소 처리보다 먼저 수행"
```

| 옵션 | 설명 |
|---|---|
| `--body <내용>` | 본문에 한 줄을 추가한다. 여러 번 지정하면 지정한 순서대로 줄이 추가된다. |
| `--issue <번호>` | `Refs: #<번호>` 푸터를 추가한다. 생략하면 브랜치명에 있는 이슈 번호를 사용한다. |
| `--no-issue` | 이슈 번호 푸터를 추가하지 않는다. |
| `--allow-protected` | main, master, develop, dev, development 브랜치에 직접 커밋한다. 사용자 승인이 필요하다. |
| `--allow-sensitive` | 민감한 파일로 의심되는 파일이 스테이징되어 있어도 커밋한다. 사용자 승인이 필요하다. |
| `--dry-run` | 검증과 메시지 미리보기만 수행하고 커밋하지 않는다. |

- 제목에 type을 포함하지 않는다. (`"feat: 로그인 추가"` ✗ → `feat "로그인 추가"` ✓)
- 스크립트는 스테이징한 변경 사항만 커밋하며, 파일을 스테이징하지 않는다.

실행 결과는 표준 출력에 `key=value` 형식으로 출력되고, 진행 로그와 경고는 표준 에러에 출력된다.

```
RESULT=committed
COMMIT=3f2a9c1
BRANCH=feat/128-add-kakao-social-login
HEADER=feat: 카카오 소셜 로그인 API 추가
FILES=3
```

- `RESULT`: 커밋했으면 `committed`, `--dry-run`으로 실행했으면 `dry-run`
- `COMMIT`: 생성한 커밋의 해시 (`--dry-run`이면 빈 값)
- `FILES`: 커밋에 포함된 파일 수

## 종료 코드별 대응

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 성공 | 결과와 경고를 사용자에게 보고한다. |
| 1 | 저장소 상태 오류 또는 커밋 실패 | 오류 메시지를 사용자에게 보고한다. pre-commit 같은 훅이 실패하면 원인을 수정한 뒤 다시 실행하고, `--no-verify`로 우회하지 않는다. |
| 2 | 인자 오류 | 메시지에 맞게 type이나 제목을 고쳐 다시 실행한다. |
| 3 | 제목 줄 72자 초과 | 제목을 줄이고, 자세한 내용은 `--body`로 옮겨 다시 실행한다. |
| 4 | 보호 브랜치에 직접 커밋 | 작업 브랜치를 새로 만들지 사용자에게 확인한다(git-branch 스킬). 사용자가 직접 커밋을 원하면 `--allow-protected`를 추가한다. |
| 5 | 스테이징한 변경 사항 없음 | 커밋할 파일을 확인해 `git add <파일 경로>`로 스테이징한 뒤 다시 실행한다. |
| 6 | 민감한 파일로 의심되는 파일 스테이징 | 파일 목록을 보여 주고 사용자에게 확인한다. 커밋에서 빼려면 `git restore --staged <파일 경로>`를 실행한다. |

## 주의 사항

- `--no-verify`, `--amend`, `git commit -a`, `git add -A`는 사용하지 않는다.
- 이미 push한 커밋은 amend나 rebase로 수정하지 않는다.
- 이 스킬은 커밋까지만 수행한다. 원격 push는 `git-push` 스킬에서 수행한다.
- 스테이징하지 않은 변경 사항이 남아 있다는 경고가 나오면, 그 파일이 커밋에 포함되지 않았다는 사실을 사용자에게 알린다.
- 파일 이름으로 판별할 수 없는 민감 정보(코드에 직접 작성한 비밀번호, API 키, 토큰)가 없는지 `git diff --cached`로 확인한다.
