# 구현 설계 문서 작성

사용자에게 받은 요구사항을 바탕으로 구현 설계 문서를 작성한다.
문서 경로 결정과 파일 생성은 `scripts/create-doc.sh`로, 작성한 문서의 검증은 `scripts/check-doc.sh`로 수행해서, 누가 작성하더라도 같은 위치에 같은 구조의 문서가 만들어지도록 한다.

## 문서 위치 규칙

- 설계 문서는 프로젝트 루트의 `docs/<YYMMDD>/<영문 문서명>.md`에 작성한다. (예: `docs/260915/kakao-social-login.md`)
- `<YYMMDD>`는 문서를 처음 작성한 날짜다. 나중에 문서를 수정해도 디렉터리를 옮기지 않는다.
- 프로젝트 루트는 Git 저장소의 최상위 디렉터리다. worktree 안에서 작성하면 그 worktree의 최상위 디렉터리가 루트가 된다.
- 문서명은 문서 주제를 간단한 영문으로 번역해서 작성하고, 영문 소문자, 숫자, `-`만 사용해 50자 이내로 작성한다. 한글 파일명은 운영체제에 따라 인코딩 문제를 일으킬 수 있기 때문이다.
- 같은 날 문서를 여러 개 작성하면 같은 날짜 디렉터리 아래에 문서명을 다르게 해서 작성한다.

## 문서 구조

`create-doc.sh`는 `templates/design-doc.md` 템플릿으로 아래 목차의 문서를 만든다. 목차의 제목과 순서는 바꾸지 않는다.

| 섹션 | 작성 내용 |
|---|---|
| 메타데이터 표 | 작성일, 작성자, 상태(초안, 검토 중, 확정), 관련 이슈 |
| 1. 개요 | 1.1 배경, 1.2 목표, 1.3 범위(포함하는 내용과 포함하지 않는 내용) |
| 2. 요구사항 | 2.1 기능 요구사항(FR-1부터 번호), 2.2 비기능 요구사항(NFR-1부터 번호) |
| 3. 설계 | 3.1 전체 구조, 3.2 주요 흐름, 3.3 데이터 모델, 3.4 API 및 인터페이스, 3.5 예외 처리 |
| 4. 구현 계획 | 4.1 작업 목록, 4.2 변경 대상 |
| 5. 테스트 계획 | 요구사항 ID별 테스트 시나리오 |
| 6. 고려 사항 | 6.1 대안 검토, 6.2 위험 요소, 6.3 미결정 사항 |
| 변경 이력 | 날짜, 변경 내용, 작성자 |

- 목차에 없는 내용이 필요하면 해당 섹션 아래에 하위 제목을 추가한다. (예: `### 3.6 캐시 전략`)
- 해당하는 내용이 없는 섹션은 지우지 말고, "해당 없음"과 그 이유를 작성한다.
- 템플릿의 안내 주석(`<!-- docs-create: ... -->`)은 해당 섹션을 작성하면서 삭제한다.
- 팀의 문서 목차를 바꾸려면 `templates/design-doc.md`를 수정한다. `check-doc.sh`도 이 템플릿의 목차를 기준으로 검증한다.

## 작성 규칙

### 요구사항 분석

- 사용자 요구사항에서 목적, 기능, 제약 조건, 범위를 추출한다.
- 목적이나 핵심 기능처럼 설계 방향을 바꾸는 내용이 불명확하면, 문서를 만들기 전에 사용자에게 질문한다.
- 세부 사항이 불명확하다는 이유로 작성을 멈추지 않는다. 합리적인 가정으로 작성하고, 가정한 내용은 6.3 미결정 사항에 적는다.
- 사용자가 말하지 않은 기능을 요구사항에 추가하지 않는다. 필요해 보이는 기능은 6.3 미결정 사항에 제안으로 적는다.

### 코드베이스 반영

- 설계를 작성하기 전에 관련 코드, 디렉터리 구조, 사용 중인 프레임워크와 라이브러리, 기존 설계 문서(`docs/`)를 확인한다.
- 설계는 프로젝트에 이미 있는 구조와 코딩 규칙을 따른다. 새로운 패턴이나 라이브러리를 도입한다면 6.1 대안 검토에 이유를 적는다.
- 존재하지 않는 클래스, 테이블, API를 이미 있는 것처럼 쓰지 않는다. 새로 만드는 대상은 "신규", 수정하는 대상은 "수정"으로 구분한다.

### 내용 작성

- 요구사항에는 FR-1, NFR-1 같은 ID를 붙이고, 4.1 작업 목록과 5. 테스트 계획에서 이 ID를 참조한다. 요구사항이 설계와 테스트에 빠짐없이 반영되었는지 추적하기 위해서다.
- 설계 결정에는 선택한 이유를 함께 쓴다.
- 구조와 흐름은 필요하면 mermaid 다이어그램(flowchart, sequenceDiagram, erDiagram)으로 표현한다.
- 코드는 전체 구현을 쓰지 않고, 인터페이스, 메서드 시그니처, 요청과 응답 예시처럼 설계를 이해하는 데 필요한 부분만 쓴다.
- 문장은 "~한다" 형태의 평서문으로 간결하게 쓴다.
- 비밀번호, API 키, 토큰, 개인정보, 운영 서버 주소 같은 민감 정보는 적지 않는다.

## 실행 절차

1. 요구사항을 분석한다. 설계 방향을 바꾸는 불명확한 내용이 있으면 사용자에게 질문한다.
2. 관련 코드와 기존 문서를 조사한다.
3. 문서 주제를 영문 문서명으로 번역하고 한국어 문서 제목을 정한 뒤 `create-doc.sh`를 실행한다.
4. 출력된 `DOC_PATH`의 문서를 열어 섹션별로 내용을 작성하고, 안내 주석을 삭제한다.
5. `check-doc.sh`로 문서를 검증한다. 문제가 있으면 모두 고친 뒤 다시 검증한다.
6. 문서 경로, 요구사항 요약, 6.3 미결정 사항을 사용자에게 보고한다.

- 기존 설계 문서를 수정해 달라는 요청이면 새 문서를 만들지 않는다. 기존 문서를 수정하고, 변경 이력 표에 행을 추가하고, 필요하면 상태를 갱신한 뒤 `check-doc.sh`로 검증한다.
- 문서 파일은 직접 만들지 않고 반드시 `create-doc.sh`로 만든다.
- 커밋은 사용자가 요청한 경우에만 git-commit 스킬로 수행한다. (예: `docs: 카카오 소셜 로그인 구현 설계 문서 작성`)

## 스크립트 사용법

스크립트는 이 SKILL.md가 있는 디렉터리를 기준으로 `scripts/`에 있다. Claude Code에서는 `<스킬 디렉터리>` 자리에 `${CLAUDE_SKILL_DIR}`를 사용한다.

### create-doc.sh

```bash
bash <스킬 디렉터리>/scripts/create-doc.sh <영문 문서명> --title "<문서 제목>" [옵션]

# 예시
bash <스킬 디렉터리>/scripts/create-doc.sh "kakao social login" --title "카카오 소셜 로그인 구현 설계" --issue 128
```

| 옵션 | 설명 |
|---|---|
| `--title <제목>` | 문서 제목을 지정한다. 필수 옵션이다. |
| `--issue <번호>` | 메타데이터 표의 관련 이슈에 이슈 번호를 적는다. |
| `--author <이름>` | 작성자를 지정한다. 생략하면 Git 설정의 `user.name`을 사용한다. |
| `--root <디렉터리>` | 프로젝트 루트를 지정한다. 생략하면 Git 저장소의 최상위 디렉터리를 사용하고, Git 저장소가 아니면 현재 디렉터리를 사용한다. |
| `--dry-run` | 문서 경로만 확인하고 파일은 만들지 않는다. |

- 문서명은 영문으로 전달한다. 대문자, 공백, 특수 문자는 스크립트가 규칙에 맞게 변환한다. (`"Kakao Social Login"` → `kakao-social-login`)
- 같은 이름의 문서가 다른 날짜 디렉터리에 있으면 경고를 출력한다. 이때는 새 문서를 만들지, 기존 문서를 수정할지 사용자에게 확인한다.

실행 결과는 표준 출력에 `key=value` 형식으로 출력되고, 진행 로그와 경고는 표준 에러에 출력된다.

```
RESULT=created
DOC_PATH=/path/to/project/docs/260915/kakao-social-login.md
DOC_RELATIVE_PATH=docs/260915/kakao-social-login.md
DOC_DATE=260915
```

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 성공 | `DOC_PATH`의 문서에 내용을 작성한다. |
| 1 | 환경 오류 (템플릿 없음, 파일 생성 실패 등) | 오류 메시지를 사용자에게 보고한다. |
| 2 | 인자 오류 | 문서명을 영문으로 번역하거나 제목을 지정해 다시 실행한다. |
| 3 | 문서명 50자 초과 | 핵심 키워드만 남겨 다시 실행한다. |
| 4 | 같은 경로의 문서가 이미 존재 | 기존 문서를 수정할지, 다른 문서명으로 새로 만들지 사용자에게 확인한다. 기존 파일을 덮어쓰지 않는다. |

### check-doc.sh

```bash
bash <스킬 디렉터리>/scripts/check-doc.sh <문서 경로>
```

다음 항목을 검사한다.

- 문서 경로가 `docs/<YYMMDD>/<영문 문서명>.md` 규칙에 맞는지
- 문서 제목(`#`)이 한 개인지
- 템플릿의 필수 섹션이 모두 같은 순서로 있고, 각 섹션에 내용이 작성되었는지
- 안내 주석이나 채우지 않은 템플릿 항목(`{{...}}`)이 남아 있지 않은지
- 메타데이터의 작성일이 날짜 디렉터리와 같은지, 상태가 초안, 검토 중, 확정 중 하나인지

```
RESULT=valid
DOC_PATH=/path/to/project/docs/260915/kakao-social-login.md
ISSUES=0
```

| 코드 | 의미 | 대응 |
|---|---|---|
| 0 | 규칙에 맞는 문서 | 결과를 사용자에게 보고한다. |
| 1 | 문서 파일이나 템플릿을 찾을 수 없음 | 경로를 확인하고 다시 실행한다. |
| 2 | 인자 오류 | 문서 경로를 하나만 전달해 다시 실행한다. |
| 3 | 문서 규칙 위반 | 표준 에러에 출력된 문제를 모두 고친 뒤 다시 검증한다. |

## 주의 사항

- 기존 문서 파일을 덮어쓰거나 삭제하지 않는다.
- 프로젝트가 `docs/` 디렉터리를 문서 사이트 소스 같은 다른 용도로 쓰고 있다면, 설계 문서를 그 아래에 둬도 되는지 사용자에게 확인한다.
- 설계 문서는 구현하기 전에 합의하기 위한 문서다. 사용자가 구현까지 요청하지 않았다면 문서를 작성한 뒤 구현을 시작하지 않는다.
